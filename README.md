# 本地生活找店助手 · lifefind-agent

用一句话说清需求，直接得到**可用**的店：

> 「晚上 8 点，6 个人吃粤菜，人均 120，3 公里内」
> → 3 家真实满足条件的店，附人均、距离、营业状态和推荐理由；地图上标出位置。

这个项目回答的是一个产品问题，不是「我调了个大模型」：

> **哪些事该交给模型，哪些必须交给代码？**

钱、距离、有没有营业 —— 有明确对错，必须用规则算；
哪家更好吃、氛围合不合适、理由怎么写 —— 主观，交给模型。

两版对照（v1 纯大模型直答 / v2 工具 + 约束校验）跑同一批 80 条 query，
差距是量出来的：

| 指标 | v1 纯大模型 | v2 工具 + 约束校验 |
|---|---|---|
| 硬约束满足率 | 59.2% | **99.5%** |
| 幻觉率 | 11.2% | **0.0%** |
| 方案可用率（≥2 家合规） | 60.0% | **75.0%** |
| 槽位抽取全字段正确率 | — | 98.8% |

数据可复现：`python src/evaluate.py`，原始报告见 `data/eval_report.json`。

## 界面

桌面窗口（WebView2），不是浏览器网页。左栏输入一句话，实时显示「它理解到的条件」；
右栏是推荐卡片，带实拍图、人均、距离、营业时间、包间提示；右侧地图标出所有候选点，
推荐店高亮。

右上角有一个**「对照」开关**——打开后并排显示「如果直接问大模型会怎样」，
有问题的店标红并写清问题，例如 `超预算(128>120)`、`虚构营业时间`。
这是整个项目最值得看的一处：把抽象结论变成肉眼可见的差别。

## 四步链路

```
用户一句话
   │
   ├─ ① 需求解析：抽出 7 个字段（人数/预算/距离/包间/菜系/忌口/时间）
   │     模型只负责「听懂」，不做任何计算
   │
   ├─ ② 检索：按菜系召回候选（本地 POI 库 或 高德周边搜索）
   │
   ├─ ③ 硬约束过滤 + 软约束排序
   │     预算 / 距离（球面距离公式）/ 营业时间 / 菜系 → 代码用 if 淘汰
   │     评分、远近、营业状态、包间信号 → 加权打分排序
   │
   └─ ④ 生成方案：把筛选后的真实字段交给模型写理由
         模型复述的价格和距离会被系统按真实数据覆盖
```

拆成四步而不是一个大 prompt，是因为出错时能定位到是哪一步的问题。

---

## 五个关键设计决策

**① 从失败反推架构，而不是先画架构再实现**

先做最笨的版本（v1：把候选列表整段丢给模型让它挑），跑完发现三类错误全部集中在
钱、距离、包间上，而对「哪家好吃」它反而很少错。设计原点来自错误的性质：
**确定性约束归代码，模糊偏好归模型。**

**② 模型复述的数字不采信**

模型会写「人均 85 元」，实际 180。所以它只负责写理由，价格和距离由系统按真实数据回填。
从机制上消除编造，而不是靠 prompt 求它别编。

**③ 菜系限定枚举值**

不限制的话模型会抽出「创意融合菜」这种库里没有的词，召回直接为空。
限定 18 个枚举后，抽取准确率可测、召回可控。

**④ 能力边界用三态表达，不用二元**

高德没有「有没有包间」这个字段。所以代码里 `has_room = None`（未知），**不是 False**。
卡片上写「包间信息未提供，建议电话确认」。营业时间同理：能查到且已关门才淘汰，
查不到就保留但标记「时间未知」。

> 模型会编造，代码也只能计算数据里有的东西。数据里没有的，就老实说不知道。

**⑤ 指标异常先查分母，不先改算法**

首轮 v2 方案可用率 42.5%，比 v1 还低。没有去调排序，而是先拉分布——发现候选池本来就是空的：
50 家店摊到 18 个菜系，每个菜系不足 3 家。扩到 198 家后指标才正常。
**数据问题改算法，只会把错误藏起来。**

## 两套数据源

| 数据源 | 说明 | 需要 key |
|---|---|---|
| `local` | 198 家模拟商户，含经纬度、人均、标签。评测走这条，保证结果可复现 | 否 |
| `amap` | 高德开放平台实时 POI：真实坐标、人均、评分、营业时间、实拍图 | 需要 `AMAP_KEY` |

```python
agent.run("6个人吃粤菜，人均120", source="local")   # 模拟数据
agent.run("6个人吃粤菜，人均120", source="amap")    # 高德真实数据
agent.run("6个人吃粤菜，人均120", source="auto")    # 有 key 用高德，没有回落本地
```

真实数据暴露的问题本身就是产品结论：搜「湘菜」返回 259 条，其中混着盖码饭和快餐，
真正标注了「湖南菜(湘菜)」的只有 2 家。**所以「菜系未确认」必须能显示给用户，
不能假装确定。**

## 三个真实案例

1. **v1 虚构包间**：query「8 个人吃湘菜，人均 90，要包间」，v1 推荐「好味饭店」，
   理由写「有包间」，实际标签里没有——8 个人到店才发现坐不下。
2. **v1 价格距离全靠猜**：query「深夜想吃烧烤，1 公里内」，v1 说「人均 85 元」，
   实际 180 元、距离 2.93 公里。
3. **v2 唯一抽错的一例**：「6 个人吃烤肉」被抽成「烧烤」而不是「日式烤肉」。
   这不是模型笨，是业务口径缺同义词映射——**模型解决不了的，要用产品规则补**。

## 快速开始

需要 Python 3.12+。推荐用 [uv](https://docs.astral.sh/uv/)，也可以直接用 pip。

```bash
git clone <this-repo>
cd lifefind-agent

# 1) 装依赖
uv sync                     # 或：pip install -e .

# 2) 配置密钥
cp .env.example .env        # 然后把你的 key 填进去

# 3) 启动图形界面
python app/main.py          # Windows 也可以双击 run_app.bat

# 或者只跑命令行对比
python src/run_demo.py
```

需求解析要用大模型，所以至少需要一个 **OpenAI 兼容接口**的 key（默认走阿里云百炼）。
高德的三个 key 是可选的，不填则地图和真实数据不可用，模拟数据仍可正常运行。

### 重跑评测

```bash
python src/evaluate.py      # 80 条 query × 2 版，约 4 分钟
```

评测结果写入 `data/eval_report.json`，指标全部规则判定，**不使用模型自评**——
同一个结果跑两次分数可能不同，经不起追问。

## 打包成 Windows 桌面程序

```bash
pyinstaller --noconfirm --windowed --name "FindShop" \
  --paths src \
  --add-data "app/ui.html;app" \
  --add-data "data/pois.json;data" \
  --add-data "data/eval_queries.json;data" \
  --collect-all webview \
  --hidden-import clr_loader --hidden-import pythonnet \
  app/main.py
```

> ⚠️ `--paths src` 不能漏。少了它，`import agent` 这类从 `src/` 动态加进路径的模块不会被打包，
> 启动直接报 `ModuleNotFoundError: No module named 'agent'`。

> ⚠️ 不要把 `.env` 一起打进安装包再分发，那等于公开你的密钥。分发时让使用者自己在
> exe 同目录放一个 `.env`。

## 已知局限

1. **没有多轮澄清**。「附近」「便宜点」这类模糊词现在只能按默认值走，
   真实产品应该反问「您能接受 3 公里内吗」。这是下一步。
2. **菜系分类依赖关键词匹配**，真实数据里脏得厉害（见上文「两套数据源」）。
   需要补同义词映射表。
3. **包间只能给弱信号**，数据源没有该字段，最终要靠用户电话确认。
4. **没有真实用户点击/转化数据**，所以只能评「约束是否满足」，
   评不了「用户是否真的喜欢」。
5. 只做了单城市、单轮次、桌面端。
